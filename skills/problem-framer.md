markdown# Problem Framer Skill

## 역할
날것의 사용자 인풋(인터뷰, 피드백, 데이터 등)을 받아
디자인 판단의 근거가 되는 구조화된 문제 정의로 변환한다.

---

## 인풋 유형

### 정성적
- 사용자 인터뷰 내용
- CS 티켓 / 슬랙 피드백
- 기획자/개발자의 요건 요청
- 정성적 리서치 메모

### 정량적
- 퍼널 이탈률 / 전환율
- 기능별 사용 빈도 데이터
- A/B 테스트 결과
- 에러 발생 빈도
- 고객군별 사용 패턴 데이터

---

## 문제 구조화 순서

### 1. 관찰 정리
날것의 인풋에서 사실만 추려낸다.
- 사용자가 실제로 한 말, 한 행동만 기록
- 정량 데이터는 수치 그대로 기록
- 해석이나 추측은 이 단계에서 섞지 않는다

### 2. 가정 vs 검증된 사실 분리
- **검증된 사실:** 데이터, 인터뷰, 실제 행동으로 확인된 것
- **가정:** 아직 확인되지 않았지만 전제하고 있는 것
- 가정은 반드시 명시하고, 검증이 필요한지 표시한다

### 3. 문제 정의 (JTBD 프레임)
사용자가 실제로 하려는 일을 중심으로 정리한다.
> "사용자는 ~할 때, ~할 수 있도록 ~을 하고 싶다."

- 기능 요청이 아니라 목적 중심으로 쓴다
- 예: "필터를 추가해달라"가 아니라 "지금 상태에서 내가 원하는 항목을 빠르게 찾고 싶다"

### 4. HMW 질문 생성
문제 정의를 디자인 탐색 질문으로 변환한다.
> "어떻게 하면 ~할 수 있을까?"

- 너무 좁지 않게 (해결책을 단정하지 않는다)
- 너무 넓지 않게 (실제로 탐색 가능한 범위로 유지한다)
- 1개 문제당 2~3개 HMW 질문을 만든다

### 5. 우선순위 판단
- 이 문제는 얼마나 많은 사용자에게 영향을 주는가
- 자주 발생하는 문제인가, 일부 케이스인가
- 정량 데이터로 뒷받침되는 문제인가, 정성 인풋만 있는 가정인가
- 지금 해결해야 하는가, 나중에 해도 되는가

---

## 작성 규칙
- 관찰과 해석을 항상 구분해서 쓴다
- 정량 데이터는 출처와 기간을 함께 명시한다
- 사용자 말을 그대로 인용할 때는 따옴표로 표시한다
- 해결책을 문제 정의 단계에서 먼저 제안하지 않는다
- 고객군이 다르면 문제 정의도 분리한다
